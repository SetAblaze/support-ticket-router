# Маршрутизация обращений в поддержку интернет-магазина

Система читает обращение клиента на английском, предлагает одну из 11 тем и очередь поддержки, ставит приоритет и отмечает риски: угрозы, мошенничество, судебные претензии. Сама она обращения никуда не отправляет: решение принимает оператор, а автоматическая отправка работает только в теневом режиме, то есть система записывает, что сделала бы, и ничего не делает.

Код лежит в пакете `support_router`. Им пользуются ноутбук этапов 1-12, скрипт обучения, HTTP-сервис на FastAPI и демонстрационный интерфейс Gradio, поэтому решение по обращению везде принимает одна функция `route_ticket`. Как части связаны между собой, описано в [docs/architecture.md](docs/architecture.md).

## Быстрый старт

**Docker.** Сервис и Prometheus одной командой (модель уже лежит в `models/`):

```bash
docker compose up --build
curl -s -X POST http://localhost:8000/v1/route -H 'content-type: application/json' \
     -d '{"text": "I want to cancel my order", "ticket_id": "CRM-1"}'
```

Документация API: http://localhost:8000/docs, Prometheus и алерты: http://localhost:9090.

Проверено на Windows с Docker Desktop: первая сборка занимает около двух минут. Если образы не скачиваются из Docker Hub, добавьте в Docker Desktop (Settings → Docker Engine) зеркало `"registry-mirrors": ["https://mirror.gcr.io"]`.

**Без Docker** (Python 3.11 или новее):

```bash
python -m venv .venv && source .venv/bin/activate   # в Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .                                  # пакет support_router из src/
python -m support_router.train                    # повторить обучение на CSV из репозитория
uvicorn support_router.api:app --port 8000        # HTTP-сервис
python app.py                                     # интерфейс Gradio на http://127.0.0.1:7860
python -m pytest -q                               # автотесты
python scripts/run_independent_benchmark.py       # независимая оценка (один прогон на выпуск)
python scripts/compare_representations.py         # сравнение признаков и режима 100 примеров
python scripts/simulate_feedback.py               # демонстрация цикла оператора
python scripts/release_manifest.py                # паспорт выпуска и experiment_id
```

**Colab.** Открыть `notebooks/Этапы_1-12_Colab.ipynb` и выполнить всё. Ноутбук читает CSV из `data/raw/`. В чистой среде первая ячейка клонирует ветку `codex/router-review-fixes` форка `SofiCholoian888/support-ticket-router`. Если рядом уже есть рабочая копия или `support-ticket-router.zip`, используется она. Адрес и ветку можно сменить в первой ячейке.

Модель загружается только при той же версии scikit-learn (1.8.0), с которой обучена, и с тем же кодом модулей решения: `load_bundle` сверяет хеши и версию и при расхождении отказывается работать. Файл модели открывается через pickle, поэтому загружайте только модель, которую обучили сами.

## API

`POST /v1/route` принимает `{"text": ..., "ticket_id": ...}` и возвращает тему, очередь, приоритет, флаги риска, причины ручной проверки и решение теневой политики. `POST /v1/route/batch` делает то же для пачки до 100 обращений. Неверные запросы получают 422, без загруженной модели сервис отвечает 503. Подробности и примеры: [docs/api.md](docs/api.md).

## Приоритет и незнакомые обращения

Сервис сначала определяет последствия для клиента. Угроза и признаки мошенничества получают P1, двойное списание или заблокированный аккаунт — P2. Для обычной просьбы действует P3. Причина повышения возвращается в `priority_reasons`.

Для предложения платёжной или аккаунтной очереди основной модели нужна уверенность от 0.95, для заказа и адреса — от 0.90, для остальных тем — от 0.85. Если фраза незнакома или уверенность ниже нужного порога, локальная MiniLM может предложить оператору другую тему. Вторая попытка включена по умолчанию. На 110 синтетических фразах без ключевых слов число верных тем выросло с 17 до 48. На 100 непрофильных обращениях MiniLM дала 6 лишних подсказок. [Бизнес-правила и пороги](docs/business_policy.md) · [Сравнение моделей на одинаковых обращениях](reports/business_cascade.json)

Решение принимается по полной матрице ожидаемых потерь `R(a|x) = Σ P(y|x) L(y,a)`, а не только по предсказанной теме. Если маршрут в предсказанную очередь дороже ручной проверки, обращение уходит оператору с причиной `EXPECTED_LOSS_PREFERS_REVIEW`. Поэтому даже высокая уверенность в CONTACT не пропустит 14% вероятности дорогой ошибки PAYMENT. [Формула и пример](docs/business_policy.md)

Цену ошибки можно задать при обучении. Например, `python -m support_router.train --out models-custom --misroute-cost PAYMENT=40` собирает отдельную модель с минимальным порогом 0.975 для оплаты.

## Обращения с несколькими просьбами

В Gradio включите **«Распознавать несколько запросов в одном обращении»**. Например, у сообщения *My payment failed and I need to change my shipping address* оператор увидит проблему с оплатой (PAYMENT) и смену адреса (SHIPPING) с двумя соответствующими очередями. Весь тикет остаётся у оператора. Угроза или сообщение о мошенничестве сохраняют свой приоритет.

Режим включается для API параметром `?detect_multiple=true`, для CSV — командой `python app.py --batch tickets.csv --out routed.csv --detect-multiple`. В обоих случаях детали доступны в `request_parts`. Английские правила ищут разные действия в частях фразы и перечислениях, в том числе внутри одной категории. Повтор одного действия объединяется. Свободные перефразировки и два одинаковых действия над разными заказами могут остаться незамеченными. [Формат ответа](docs/api.md#режим-нескольких-запросов)

На 15 синтетических обращениях с несколькими темами режим выделил просьбы во всех 15. На 3 122 однотематических обращениях Bitext и 220 авторских однотематических примерах ни одно обращение не разделилось. Эти примеры использовались при разработке правил.

На независимом наборе из 12 многотемных обращений точное совпадение 9/12,
precision по интентам 1.000, recall 0.750. Ложных разделений нет: 0 из 3 122,
0 из 220 и 0 из 55 однотемных независимых обращений. Три промаха — это
перефразировки, которые правила не узнают. На независимом наборе правила не
настраивались. Качество на реальных обращениях пока неизвестно. [Результаты проверки](reports/review_benchmark.json)

## Данные и модель

В репозитории лежит оригинальный CSV из набора *Bitext Sample Pre-built Customer Support Dataset for English* (© Bitext Innovations, 2020). SHA-256 исходного файла — `19a3031d649ce432202acd807630b1b52884507185f32832d58714f3fac7d82b`. Лицензия данных — CDLA-Sharing-1.0. [Источник на Kaggle](https://www.kaggle.com/datasets/bitext/training-dataset-for-chatbotsvirtual-assistants) · [Описание Bitext](data/raw/README.txt) · [Лицензия данных](data/raw/LICENSE.txt)

Bitext Customer Support: 21 534 обращения, 11 тем, 27 интентов, фразы синтетические, по шаблонам. После очистки и удаления дублей осталось 19 700 фраз. Похожие фразы объединены в 3 646 групп, и каждая группа целиком попадает в одну часть выборки: обучение 11 970, калибровка 2 240, выбор порога 2 368, test 3 122.

Модель: TF-IDF по словам (1-2) и по буквам (3-5) и LinearSVC (C=1), вероятности получены сигмоидной калибровкой на отдельной части. Она выбрана из 11 конфигураций по проверке LOIO: интент целиком убирается из обучения, и модель должна отнести его фразы к правильной теме.

LOIO — это выбор архитектуры, а не независимая оценка: все 25 интентов участвовали в выборе. Разница MiniLM + LogReg против выбранной LinearSVC на этих же интентах имеет интервал [−11.9; +7.5] п.п., то есть ноль внутри. Независимый набор показал, что на новых формулировках выбранная модель не лучше базовой, а MiniLM + LogReg заметно лучше. Поэтому смена основной модели вынесена в следующий выпуск, а не сделана по тому же набору.

### Независимая оценка после аудита

Для независимой проверки создан замороженный набор `independent-v1-2026-11-23`
(110 размеченных фраз в двух режимах, 20 OOD, 16 риск-примеров, 12 многотемных).
Протокол зафиксирован до первого прогона: [docs/independent_benchmark_protocol.md](docs/independent_benchmark_protocol.md).
Точных совпадений с Bitext и наборами разработки нет, максимальное лексическое
сходство с Bitext 0.794.

| Режим | Выбранная модель | Базовая TF-IDF + LogReg |
|---|---:|---:|
| `natural`, top-1 из 55 | 50.9% | 49.1% |
| `no_keywords`, top-1 из 55 | 21.8% | 27.3% |

На новых формулировках преимущество выбранной модели не подтверждается, а на
`no_keywords` она уступает базовой. Это главный вывод независимой проверки:

### Сравнение признаков и 100 размеченных примеров

| Признаки | Полный train, `natural` | Полный train, `no_keywords` | 100 примеров, `natural` | 100 примеров, `no_keywords` |
|---|---:|---:|---:|---:|
| TF-IDF + LinearSVC | 54.5% | 27.3% | 43.6% ± 4.7 | 20.4% ± 4.2 |
| MiniLM + LogReg | 76.4% | 58.2% | 77.8% ± 2.1 | 59.3% ± 3.6 |

Предобученные эмбеддинги обобщают заметно лучше TF-IDF, и преимущество
сохраняется при 100 размеченных примерах: регуляризация выбиралась только
внутри этих 100 строк, по пяти seeds. Это кандидат на следующую основную
модель, но выбирать его нужно на новом замороженном наборе, а не на этом.
Zero/few-shot LLM в этом окружении не запускался: отчёт фиксирует `NOT_RUN`,
а не выдуманные числа. [Полные результаты](reports/representation_comparison.json)

### Предыдущий эксперимент с двумя самостоятельными моделями

На тех же разбиениях отдельно проверили MiniLM + LogReg (`semantic_lr_C1`). У каждой модели собственная сигмоидная калибровка и два порога, подобранные на val и OOD-dev. Top-3 засчитывает обращение, если правильная тема вошла в три предложения оператору.

| Авторские наборы | TF-IDF + LinearSVC | MiniLM + LogReg |
|---|---:|---:|
| Обычные фразы, верная тема в top-1 / top-3 из 110 | 98 / 107 | 106 / 110 |
| Без слов-подсказок, верная тема в top-1 / top-3 из 110 | 17 / 41 | 72 / 102 |
| Уверенность / минимальное сходство | 0.85 / 0.45 | 0.70 / 0.45 |
| Автоматических рекомендаций из 220 | 66 | 81 |
| Ошибочная очередь среди автоматических рекомендаций | 1 из 66 | 5 из 81 |
| Автоматических рекомендаций на 100 обращениях вне области задачи | 5 | 11 |

MiniLM чаще подсказывает правильную тему на перефразировках. Его теневая политика также чаще принимает обращения в ошибочную очередь. В текущем сервисе TF-IDF + LinearSVC отвечает первым, MiniLM подключается выборочно. Наборы авторские и уже использованы для анализа. Следующую версию стоит сравнивать на новых заранее зафиксированных сценариях.

После установки пакета и создания частей данных командой обучения выполните `python scripts/benchmark_review.py`. Скрипт сверяет хеши частей с паспортом релизной модели и записывает `reports/review_benchmark.json` с метриками моделей и precision/recall правил риска. Для MiniLM нужны x86-64 с AVX2 и файлы энкодера из `models/encoder/`. [Результаты эксперимента](reports/review_benchmark.json)

Что было бы, если включить автоотправку (теневой режим с порогами 0.85 по уверенности и 0.45 по сходству плюс проверка ожидаемых потерь): на test система отправила бы сама 97.98% обращений (3 059 из 3 122) и не ошиблась бы с очередью ни разу. Ожидаемые потери заблокировали все шесть ошибок PAYMENT → REFUNDS, которые проходили старые пороги; цена — 9 решений больше не принимаются автоматически. На независимом наборе покрытие падает до 18.2% (`natural`) и 7.3% (`no_keywords`), а из 4 авторекомендаций в `no_keywords` две ошибочны. В рабочем режиме система не отправила сама ни одного обращения. Автоотправка выключена до проверки на реальных обращениях. ## Тесты

`python -m pytest -q` проверяет пакет, Gradio, FastAPI, мониторинг и исправления после аудита (263 теста, 1 пропущен). Для полного прогона нужны энкодер MiniLM и `promtool` в PATH. Правила Prometheus можно проверить отдельно командой `promtool test rules monitoring/alert_rules_test.yml`.

В наборе из 18 авторских примеров есть прямые сообщения об угрозах и мошенничестве, отрицания, цитаты и нейтральные фразы. Например, «I will make you a list of the missing items» получает P3, а «I see a fraudulent charge on my card» — P1 с флагом мошенничества. Метрики по этому набору описывают регрессионные примеры. Для оценки на пользовательском потоке нужна независимая разметка. [Набор проверок](data/eval/risk_regression.csv)


## Мониторинг

Сервис отдаёт метрики Prometheus на `/metrics`: запросы и время ответа, решения по статусам и приоритетам, флаги риска, причины, уверенность, сходство с обучением, ошибки модели. Текст обращения в метрики и журнал не попадает. Одиннадцать правил алертов следят за доступностью, ошибками, задержкой, отсутствием потока, всплеском P1, сдвигом входящих текстов и тем, что рабочий режим не начал отправлять обращения сам. Что делать по каждому алерту: [docs/runbook.md](docs/runbook.md).

## Ограничения

- Данные синтетические: и Bitext, и новые фразы этапа 11, и независимый набор написаны не настоящими клиентами.
- Независимый набор авторский, без экспертной разметки. Он заморожен протоколом и не использовался для настройки.
- На независимом наборе выбранная модель не показала преимущества над базовой; MiniLM + LogReg лучше, но требует нового набора для выбора.
- Правила рисков демонстрационные: на независимых положительных примерах recall 50%, поэтому это не защитный контур.
- Автоотправка выключена, пока нет реальных обращений: не меньше 300 по темам и 200 не по адресу.
- Уведомления по алертам (Alertmanager) не настроены: правила видны в Prometheus.
