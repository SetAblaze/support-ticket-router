# Маршрутизация обращений в поддержку интернет-магазина

Система читает обращение клиента на английском, предлагает одну из 11 тем и очередь поддержки, ставит приоритет и отмечает риски: угрозы, мошенничество, судебные претензии. Сама она обращения никуда не отправляет: решение принимает оператор, а автоматическая отправка работает только в теневом режиме, то есть система записывает, что сделала бы, и ничего не делает.

Код лежит в пакете `support_router`. Им пользуются ноутбук этапов 1-12, скрипт обучения, HTTP-сервис на FastAPI и демонстрационный интерфейс Gradio, поэтому решение по обращению везде принимает одна функция `route_ticket`. Как части связаны между собой, описано в [docs/architecture.md](docs/architecture.md).

## Быстрый старт

**Docker.** Сервис и Prometheus одной командой (модель уже лежит в `models/`):

```bash
docker compose up --build
curl -s -X POST http://localhost:8000/v1/route -H 'content-type: application/json' \
     -d '{"text": "I want to cancel my order", "ticket_id": "CRM-1"}'
```

Документация API: http://localhost:8000/docs, Prometheus и алерты: http://localhost:9090.

Проверено на Windows с Docker Desktop: первая сборка занимает около двух минут. Если образы не скачиваются из Docker Hub, добавьте в Docker Desktop (Settings → Docker Engine) зеркало `"registry-mirrors": ["https://mirror.gcr.io"]`.

**Без Docker** (Python 3.11 или новее):

```bash
python -m venv .venv && source .venv/bin/activate   # в Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .                                  # пакет support_router из src/
python -m support_router.train                    # обучить модель заново (нужен CSV Bitext в data/raw)
uvicorn support_router.api:app --port 8000        # HTTP-сервис
python app.py                                     # интерфейс Gradio на http://127.0.0.1:7860
python -m pytest -q                               # автотесты
```

**Colab.** Открыть `notebooks/Этапы_1-12_Colab.ipynb` и выполнить всё. Первая ячейка берёт код проекта из GitHub (переменная `PROJECT_REPO`) или из загруженного архива, затем попросит CSV датасета.

Модель загружается только при той же версии scikit-learn (1.8.0), с которой обучена, и с тем же кодом модулей решения: `load_bundle` сверяет хеши и версию и при расхождении отказывается работать. Файл модели открывается через pickle, поэтому загружайте только модель, которую обучили сами.

## API

`POST /v1/route` принимает `{"text": ..., "ticket_id": ...}` и возвращает тему, очередь, приоритет, флаги риска, причины ручной проверки и решение теневой политики. `POST /v1/route/batch` делает то же для пачки до 100 обращений. Неверные запросы получают 422, без загруженной модели сервис отвечает 503. Подробности и примеры: [docs/api.md](docs/api.md).

## Данные и модель

Bitext Customer Support: 21 534 обращения, 11 тем, 27 интентов, фразы синтетические, по шаблонам. После очистки и удаления дублей осталось 19 700 фраз. Похожие фразы объединены в 3 646 групп, и каждая группа целиком попадает в одну часть выборки: обучение 11 970, калибровка 2 240, выбор порога 2 368, test 3 122.

Модель: TF-IDF по словам (1-2) и по буквам (3-5) и LinearSVC (C=1), вероятности получены сигмоидной калибровкой на отдельной части. Она выбрана из 11 конфигураций, включая эмбеддинги MiniLM, по проверке LOIO: интент целиком убирается из обучения, и модель должна отнести его фразы к правильной теме.

## Результаты

| Проверка | Что показывает | Выбранная модель | Базовая (TF-IDF + LogReg) |
|---|---|---|---|
| Test Bitext, 3 122 фразы | те же шаблоны, что в обучении | macro-F1 0.996, 10 ошибок | macro-F1 0.994, 16 ошибок |
| LOIO, 25 интентов | целиком новые интенты | 81.8% | 68.6% |
| Новые фразы обычными словами, 110 | написаны вне датасета | 89.1% | 81.8% |
| Новые фразы без слов-подсказок, 110 | написаны вне датасета | 15.5% | 15.5% |

На test обе модели почти безошибочны, потому что test собран из тех же шаблонов. Реальную разницу показывают LOIO и новые фразы: модель узнаёт слова, а не смысл.

Что было бы, если включить автоотправку (теневой режим с порогами 0.85 по уверенности и 0.45 по сходству): на test система отправила бы сама 98.3% обращений и ошиблась бы с очередью 6 раз из 3 068, на 220 новых фразах отправила бы 66 и ошиблась 1 раз, из 100 обращений не по адресу отправила бы 5. В рабочем режиме она не отправила сама ни одного обращения. Автоотправка выключена до проверки на реальных обращениях. Все цифры собраны в `reports/results.json` и ноутбуке.

## Тесты

`python -m pytest -q` запускает 222 теста: этапы 1-9, приложение Gradio, нестандартные входы, HTTP API (неверные запросы, пустые обращения, маршрутизация, готовность), метрики и правила алертов. Четыре теста записаны как известные пропуски правил рисков (`xfail`): фразы вроде «fraudulent charge», которые правила сознательно не ловят без экспертной разметки. Два теста семантического энкодера пропускаются, если нет доступа к Hugging Face, а проверка правил алертов пропускается, если не установлен `promtool` (в Colab его нет). Вручную правила проверяет `promtool test rules monitoring/alert_rules_test.yml`.

## Мониторинг

Сервис отдаёт метрики Prometheus на `/metrics`: запросы и время ответа, решения по статусам и приоритетам, флаги риска, причины, уверенность, сходство с обучением, ошибки модели. Текст обращения в метрики и журнал не попадает. Одиннадцать правил алертов следят за доступностью, ошибками, задержкой, отсутствием потока, всплеском P1, сдвигом входящих текстов и тем, что рабочий режим не начал отправлять обращения сам. Что делать по каждому алерту: [docs/runbook.md](docs/runbook.md).

## Ограничения

- Данные синтетические: и Bitext, и новые фразы этапа 11 написаны не настоящими клиентами.
- Правила рисков демонстрационные: их полнота не измерена на экспертной разметке.
- Автоотправка выключена, пока нет реальных обращений: не меньше 300 по темам и 200 не по адресу.
- Уведомления по алертам (Alertmanager) не настроены: правила видны в Prometheus.
