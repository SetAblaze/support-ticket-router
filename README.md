# Маршрутизация обращений в поддержку интернет-магазина

Система читает обращение клиента на английском, предлагает одну из 11 тем и очередь поддержки, ставит приоритет и отмечает риски: угрозы, мошенничество, судебные претензии. Сама она обращения никуда не отправляет: решение принимает оператор, а автоматическая отправка работает только в теневом режиме, то есть система записывает, что сделала бы, и ничего не делает.

Код лежит в пакете `support_router`. Им пользуются ноутбук этапов 1-12, скрипт обучения, HTTP-сервис на FastAPI и демонстрационный интерфейс Gradio, поэтому решение по обращению везде принимает одна функция `route_ticket`. Как части связаны между собой, описано в [docs/architecture.md](docs/architecture.md).

## Быстрый старт

**Docker.** Сервис и Prometheus одной командой (модель уже лежит в `models/`):

```bash
docker compose up --build
curl -s -X POST http://localhost:8000/v1/route -H 'content-type: application/json' \
     -d '{"text": "I want to cancel my order", "ticket_id": "CRM-1"}'
```

Документация API: http://localhost:8000/docs, Prometheus и алерты: http://localhost:9090.

Проверено на Windows с Docker Desktop: первая сборка занимает около двух минут. Если образы не скачиваются из Docker Hub, добавьте в Docker Desktop (Settings → Docker Engine) зеркало `"registry-mirrors": ["https://mirror.gcr.io"]`.

**Без Docker** (Python 3.11 или новее):

```bash
python -m venv .venv && source .venv/bin/activate   # в Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .                                  # пакет support_router из src/
python -m support_router.train                    # повторить обучение на CSV из репозитория
uvicorn support_router.api:app --port 8000        # HTTP-сервис
python app.py                                     # интерфейс Gradio на http://127.0.0.1:7860
python -m pytest -q                               # автотесты
```

**Colab.** Открыть `notebooks/Этапы_1-12_Colab.ipynb` и выполнить всё. Ноутбук читает CSV из `data/raw/`. В чистой среде первая ячейка клонирует ветку `codex/router-review-fixes` форка `SofiCholoian888/support-ticket-router`. Если рядом уже есть рабочая копия или `support-ticket-router.zip`, используется она. Адрес и ветку можно сменить в первой ячейке.

Модель загружается только при той же версии scikit-learn (1.8.0), с которой обучена, и с тем же кодом модулей решения: `load_bundle` сверяет хеши и версию и при расхождении отказывается работать. Файл модели открывается через pickle, поэтому загружайте только модель, которую обучили сами.

## API

`POST /v1/route` принимает `{"text": ..., "ticket_id": ...}` и возвращает тему, очередь, приоритет, флаги риска, причины ручной проверки и решение теневой политики. `POST /v1/route/batch` делает то же для пачки до 100 обращений. Неверные запросы получают 422, без загруженной модели сервис отвечает 503. Подробности и примеры: [docs/api.md](docs/api.md).

## Обращения с несколькими просьбами

В Gradio включите **«Распознавать несколько запросов в одном обращении»**. Например, у сообщения *My payment failed and I need to change my shipping address* оператор увидит проблему с оплатой (PAYMENT) и смену адреса (SHIPPING) с двумя соответствующими очередями. Весь тикет остаётся у оператора. Угроза или сообщение о мошенничестве сохраняют свой приоритет.

Режим включается для API параметром `?detect_multiple=true`, для CSV — командой `python app.py --batch tickets.csv --out routed.csv --detect-multiple`. В обоих случаях детали доступны в `request_parts`. Английские правила ищут разные действия в частях фразы и перечислениях, в том числе внутри одной категории. Повтор одного действия объединяется. Свободные перефразировки и два одинаковых действия над разными заказами могут остаться незамеченными. [Формат ответа](docs/api.md#режим-нескольких-запросов)

На 15 синтетических обращениях с несколькими темами режим выделил просьбы во всех 15. На 3 122 однотематических обращениях Bitext и 220 авторских однотематических примерах ни одно обращение не разделилось. Эти примеры использовались при разработке правил. Качество на реальных обращениях пока неизвестно. [Результаты проверки](reports/review_benchmark.json)

## Данные и модель

В репозитории лежит оригинальный CSV из набора *Bitext Sample Pre-built Customer Support Dataset for English* (© Bitext Innovations, 2020). SHA-256 исходного файла — `19a3031d649ce432202acd807630b1b52884507185f32832d58714f3fac7d82b`. Лицензия данных — CDLA-Sharing-1.0. [Источник на Kaggle](https://www.kaggle.com/datasets/bitext/training-dataset-for-chatbotsvirtual-assistants) · [Описание Bitext](data/raw/README.txt) · [Лицензия данных](data/raw/LICENSE.txt)

Bitext Customer Support: 21 534 обращения, 11 тем, 27 интентов, фразы синтетические, по шаблонам. После очистки и удаления дублей осталось 19 700 фраз. Похожие фразы объединены в 3 646 групп, и каждая группа целиком попадает в одну часть выборки: обучение 11 970, калибровка 2 240, выбор порога 2 368, test 3 122.

Модель: TF-IDF по словам (1-2) и по буквам (3-5) и LinearSVC (C=1), вероятности получены сигмоидной калибровкой на отдельной части. Она выбрана из 11 конфигураций, включая эмбеддинги MiniLM, по проверке LOIO: интент целиком убирается из обучения, и модель должна отнести его фразы к правильной теме.

## Результаты

| Проверка | Что показывает | Выбранная модель | Базовая (TF-IDF + LogReg) |
|---|---|---|---|
| Test Bitext, 3 122 фразы | те же шаблоны, что в обучении | macro-F1 0.996, 10 ошибок | macro-F1 0.994, 16 ошибок |
| LOIO, 25 интентов | целиком новые интенты | 81.8% | 68.6% |
| Новые фразы обычными словами, 110 | написаны вне датасета | 89.1% | 81.8% |
| Новые фразы без слов-подсказок, 110 | написаны вне датасета | 15.5% | 15.5% |

Все 10 ошибок выбранной модели на test относятся к PAYMENT → REFUNDS. Это две группы по пять вариантов отклонённого перевода или транзакции. Шесть из этих ошибок прошли оба теневых порога. Из 3 122 тестовых фраз у 448 есть сосед в train со сходством ≥ 0.85 по диагностике разбиения. В LOIO самые сложные интенты — `track_order` (36.1% верных тем) и `check_refund_policy` (36.8%). Все 25 интентов участвовали в выборе модели. В таблице 11 конфигураций, из них 10 различимы в LOIO: авторские дополнения `semantic_aug_lr_C1` исключаются внутри фолдов. [Ошибки по фразам](reports/test_predictions.csv) · [Сравнение LOIO](reports/loio_comparison_all_11.csv)

### Подсказки оператору и ошибки теневой политики

На тех же разбиениях отдельно проверили MiniLM + LogReg (`semantic_lr_C1`). У каждой модели собственная сигмоидная калибровка и два порога, подобранные на val и OOD-dev. Top-3 засчитывает обращение, если правильная тема вошла в три предложения оператору.

| Авторские наборы | TF-IDF + LinearSVC | MiniLM + LogReg |
|---|---:|---:|
| Обычные фразы, верная тема в top-1 / top-3 из 110 | 98 / 107 | 106 / 110 |
| Без слов-подсказок, верная тема в top-1 / top-3 из 110 | 17 / 41 | 72 / 102 |
| Уверенность / минимальное сходство | 0.85 / 0.45 | 0.70 / 0.45 |
| Автоматических рекомендаций из 220 | 66 | 81 |
| Ошибочная очередь среди автоматических рекомендаций | 1 из 66 | 5 из 81 |
| Автоматических рекомендаций на 100 обращениях вне области задачи | 5 | 11 |

MiniLM чаще подсказывает правильную тему на перефразировках. Его теневая политика также чаще принимает обращения в ошибочную очередь. В сервисе используется TF-IDF + LinearSVC с ручным решением оператора. Наборы авторские и уже использованы для анализа. Следующую версию стоит сравнивать на новых заранее зафиксированных сценариях.

После установки пакета и создания частей данных командой обучения выполните `python scripts/benchmark_review.py`. Скрипт сверяет хеши частей с паспортом релизной модели и записывает `reports/review_benchmark.json` с метриками моделей и precision/recall правил риска. Для MiniLM нужны x86-64 с AVX2 и энкодер, который скачивается при первом запуске. [Результаты эксперимента](reports/review_benchmark.json)

Что было бы, если включить автоотправку (теневой режим с порогами 0.85 по уверенности и 0.45 по сходству): на test система отправила бы сама 98.3% обращений и ошиблась бы с очередью 6 раз из 3 068, на 220 новых фразах отправила бы 66 и ошиблась 1 раз, из 100 обращений не по адресу отправила бы 5. В рабочем режиме она не отправила сама ни одного обращения. Автоотправка выключена до проверки на реальных обращениях. Все цифры собраны в `reports/results.json` и ноутбуке.

## Тесты

`python -m pytest -q` проверяет пакет, Gradio, FastAPI и мониторинг. Для полного прогона нужны энкодер MiniLM и `promtool` в PATH. Правила Prometheus можно проверить отдельно командой `promtool test rules monitoring/alert_rules_test.yml`.

В наборе из 18 авторских примеров есть прямые сообщения об угрозах и мошенничестве, отрицания, цитаты и нейтральные фразы. Например, «I will make you a list of the missing items» получает P3, а «I see a fraudulent charge on my card» — P1 с флагом мошенничества. Метрики по этому набору описывают регрессионные примеры. Для оценки на пользовательском потоке нужна независимая разметка. [Набор проверок](data/eval/risk_regression.csv)


## Мониторинг

Сервис отдаёт метрики Prometheus на `/metrics`: запросы и время ответа, решения по статусам и приоритетам, флаги риска, причины, уверенность, сходство с обучением, ошибки модели. Текст обращения в метрики и журнал не попадает. Одиннадцать правил алертов следят за доступностью, ошибками, задержкой, отсутствием потока, всплеском P1, сдвигом входящих текстов и тем, что рабочий режим не начал отправлять обращения сам. Что делать по каждому алерту: [docs/runbook.md](docs/runbook.md).

## Ограничения

- Данные синтетические: и Bitext, и новые фразы этапа 11 написаны не настоящими клиентами.
- Правила рисков демонстрационные: их полнота не измерена на экспертной разметке.
- Автоотправка выключена, пока нет реальных обращений: не меньше 300 по темам и 200 не по адресу.
- Уведомления по алертам (Alertmanager) не настроены: правила видны в Prometheus.
