# Мониторинг и действия при сбоях

Сервис маршрутизации отдаёт метрики Prometheus на `/metrics`, а Prometheus из `docker-compose.yml` каждые 15 секунд их собирает и проверяет правила из `monitoring/alert_rules.yml`. Ниже описано, что значит каждый алерт, как его проверить и что делать.

Главное правило безопасности: сервис сам ничего никуда не отправляет. Если он упал или отвечает ошибкой, CRM направляет обращения в общую ручную очередь `Queue_Manual_Review`. Поддержка при этом продолжает работать, пропадают только подсказки темы и приоритета. Поэтому при любом сбое первым делом проверьте, что этот запасной путь в CRM работает.

## Что собирается

| Метрика | Что показывает |
|---|---|
| `router_http_requests_total{endpoint, method, status_code}` | запросы к сервису и коды ответов |
| `router_http_request_duration_seconds` | время ответа, гистограмма |
| `router_decisions_total{status, queue, priority}` | решения рабочего режима |
| `router_shadow_decisions_total{status}` | что сделала бы теневая политика |
| `router_suggested_category_total{category}` | какие темы предлагает модель |
| `router_risk_flags_total{flag}`, `router_reason_codes_total{reason}` | флаги риска и причины ручной проверки |
| `router_confidence`, `router_training_similarity` | уверенность модели и сходство с обучающими фразами |
| `router_text_length_chars` | длина обращений |
| `router_model_errors_total` | обращения, которые модель не смогла оценить |
| `router_model_loaded`, `router_model_info{model_id, ...}` | загружена ли модель и какая именно |
| `router_feedback_total{outcome, proposed_category, final_category}` | подтверждённые и исправленные оператором решения |

Текст обращения не попадает ни в метрики, ни в журнал. В журнале сервиса (`docker compose logs api`) на каждое обращение одна JSON-строка: номер запроса, номер обращения из CRM, статус, тема, очередь, приоритет, флаги, причины, уверенность, сходство и длина текста.

## Где смотреть

- Prometheus: http://localhost:9090, вкладка Alerts показывает сработавшие правила, вкладка Graph строит запросы, например `sum by (status) (rate(router_decisions_total[5m]))`.
- Готовность и причина отказа: `curl http://localhost:8000/ready`.
- Паспорт загруженной модели: `curl http://localhost:8000/v1/model`.
- Журнал: `docker compose logs --tail 200 api`.

Пороги для долей обращений взяты из проверок этапа 11: на test Bitext, на 220 новых фразах и на 100 обращениях не по адресу. После месяца реального потока их нужно пересчитать по этому потоку.

## Обратная связь оператора

Подтверждение или исправление оператора — единственный источник проверенной
разметки после внедрения. Контур устроен так:

1. Оператор видит предложенную тему и либо подтверждает её, либо выбирает другую.
2. `support_router.feedback.make_feedback_event` создаёт запись без сырого
   текста: хеш текста, предложенная и итоговая темы, уверенность, версия модели
   и политики.
3. Записи складываются в JSONL через `append_feedback`; метрика
   `router_feedback_total` показывает поток подтверждений и исправлений.
4. `feedback_metrics` считает измеренную точность по предложенной теме и
   помечает категории с малой поддержкой как `INSUFFICIENT_SUPPORT`.
5. `retraining_candidates` возвращает только исправленные примеры — они несут
   новую информацию для следующего обучения.

Демонстрация на замороженном наборе:
`python scripts/simulate_feedback.py` → `reports/feedback_simulation.json`.
Симуляция с идеальным оператором восстанавливает точность предложений; с
ошибкой оператора 10–20% видно, как ошибки оператора попадают в метрику.
Подтверждение оператора не заменяет внешний аудит: ошибочное предложение,
которое оператор подтвердил не глядя, будет выглядеть верным.

## Независимая оценка и версия выпуска

- Независимый набор: `python scripts/run_independent_benchmark.py` →
  `reports/independent_benchmark.json`. Набор заморожен протоколом
  `docs/independent_benchmark_protocol.md`. Его нельзя использовать для
  настройки порогов, правил или промптов: после первого прогона фразы не
  меняются.
- Сравнение признаков и режима 100 примеров:
  `python scripts/compare_representations.py` →
  `reports/representation_comparison.json`.
- Версия выпуска: `python scripts/release_manifest.py` →
  `reports/release_manifest.json`. В манифесте Git commit, `model_id`, хеш
  артефакта, хеш данных, версия политики, хеши наборов оценки и отчётов,
  а также `experiment_id`. Сравнивать отчёты можно только при совпадении
  `experiment_id`, хешей наборов и версии политики. Смена политики меняет
  решения без изменения классификатора, поэтому это другой эксперимент.

## Алерты

### RouterDown

**Что значит.** Prometheus больше 2 минут не может получить метрики: процесс упал, контейнер перезапускается или сеть между контейнерами сломана.

**Как проверить.** `docker compose ps`, затем `docker compose logs --tail 100 api` и `curl http://localhost:8000/health`.

**Что делать.** Убедиться, что CRM отправляет обращения в ручную очередь. Перезапустить сервис: `docker compose restart api`. Если не поднимается, вернуть предыдущий образ (`docker compose up -d` с прежним тегом) и разобраться по журналу.

### RouterModelNotLoaded

**Что значит.** Процесс жив, но модель не прошла проверки при загрузке, и `/v1/route` отвечает 503. Обычные причины: модель обучена другой версией scikit-learn, изменился код модулей решения (`config`, `text`, `models`, `rules`, `routing`, `business`, `cascade` и вспомогательные), файл модели повреждён или его нет.

**Как проверить.** `curl http://localhost:8000/ready` покажет причину. Сравните `scikit-learn` в `models/router_meta.json` с `requirements-api.txt`.

**Что делать.** Переобучить модель этим же кодом (`python -m support_router.train`) и пересобрать образ или вернуть предыдущий образ, где код и модель совпадают. Отключать проверки нельзя: они защищают от модели, которая тихо решает иначе, чем проверенная.

### RouterHighErrorRate

**Что значит.** Больше 2% ответов за 5 минут заканчиваются ошибкой 5xx. Ошибки 422 (неверный запрос) сюда не входят: это проблема вызывающей стороны, их видно в `router_http_requests_total{status_code="422"}`.

**Как проверить.** В журнале найти события с `status_code` 500 и номером запроса (`request_id`), там же будет трассировка ошибки.

**Что делать.** Если ошибки начались после выкладки, откатить образ. Если на отдельных обращениях, воспроизвести запрос локально по длине текста и номеру обращения из CRM.

### RouterSlowResponses

**Что значит.** 95% ответов `/v1/route` медленнее 0.5 секунды, хотя при проверке укладывались в 0.04 секунды.

**Как проверить.** `rate(router_http_request_duration_seconds_count[5m])` покажет, не вырос ли поток; `router_text_length_chars` покажет, не пошли ли очень длинные тексты; `docker stats` покажет загрузку процессора.

**Что делать.** При росте потока добавить экземпляры сервиса за балансировщиком или перевести CRM на `/v1/route/batch` пачками до 100 обращений. Длинные тексты уже ограничены 5000 символами.

### RouterNoTraffic

**Что значит.** 45 минут не было ни одного запроса на маршрутизацию. Сервис здоров, но к нему никто не обращается: скорее всего, сломалась интеграция с CRM или поменялся адрес.

**Как проверить.** Посмотреть журнал CRM и `router_http_requests_total` по кодам ответа: нет ли всплеска 4xx перед паузой. Ночью и в выходные поток может и правда быть пустым, тогда алерт можно погасить.

**Что делать.** Восстановить вызов из CRM; пока он не работает, обращения идут в ручную очередь без подсказок.

### RouterAutoSendWhileDisabled

**Что значит.** Рабочий режим вернул статус `AUTO_RECOMMENDED`, то есть система решила отправить обращение сама. В выпущенной политике автоотправка выключена, значит загружена не та модель или не та политика. Это самый опасный алерт: обращения могут уйти в очередь без проверки человеком.

**Как проверить.** `curl http://localhost:8000/v1/model`: поле `policy.auto_enabled` должно быть `false`, сравните `model_id` с ожидаемым.

**Что делать.** Немедленно вернуть предыдущий образ. Включать автоотправку можно только отдельным решением после проверки на реальных обращениях (не меньше 300 по темам и 200 не по адресу) и согласования с бизнесом.

### RouterModelErrors

**Что значит.** Модель не смогла оценить обращения, они получили статус `MODEL_ERROR` и ушли оператору без темы.

**Как проверить.** В журнале события `decision` со статусом `MODEL_ERROR`: какая длина текста, какой `model_id`.

**Что делать.** Если ошибок много, откатить модель. Единичные ошибки сохранить с номером обращения для разбора.

### RouterRiskSpike

**Что значит.** За час больше 5% обращений получили приоритет P1 (угроза или мошенничество). На test таких было 0.16%.

**Как проверить.** `sum by (flag) (increase(router_risk_flags_total[1h]))` покажет, какой флаг вырос. Выборочно посмотреть сами обращения в CRM по номерам из журнала.

**Что делать.** Если это реальная волна (например, атака на аккаунты), предупредить специалистов и службу безопасности. Если правило ловит обычные обращения, записать примеры: правила рисков демонстрационные и требуют экспертной разметки.

### RouterInputDrift

**Что значит.** Больше 60% обращений за час не похожи на обучающие фразы (сходство ниже 0.45). На test таких 0.4%, на новых фразах этапа 11 57%, на обращениях не по адресу 70%. Поток изменился: новые темы, другой язык, рассылка спама.

**Как проверить.** `sum by (category) (increase(router_suggested_category_total[1h]))` и доля `POSSIBLY_UNSUPPORTED_LANGUAGE` в `router_reason_codes_total`.

**Что делать.** Выгрузить из CRM выборку таких обращений, разметить и решить, нужна ли новая тема или переобучение. Пока поток не похож на обучающий, теневой режим чаще отдаёт оператору: это безопасно.

### RouterUnsupportedLanguageSurge

**Что значит.** Больше 10% обращений не на английском. Модель понимает только английский, такие обращения уходят оператору без темы.

**Как проверить.** Доля причины `POSSIBLY_UNSUPPORTED_LANGUAGE` в `router_reason_codes_total` за последние часы.

**Что делать.** Сообщить владельцу продукта: если это устойчивый поток, нужна модель для этого языка или настоящий определитель языка.

### RouterShadowCoverageDrop

**Что значит.** Доля обращений, которые теневая политика отправила бы сама, за 6 часов упала вдвое против среднего за неделю. Модель стала реже уверена: поменялся поток или сломалась предобработка.

**Как проверить.** Гистограммы `router_confidence` и `router_training_similarity`: сдвинулись ли они вниз; совпадает ли `model_id` с прежним.

**Что делать.** Если модель новая, сравнить её с прежней на последних обращениях и при необходимости откатить. Если поток новый, действовать как при RouterInputDrift.

## Как это проверялось

Синтаксис правил и их поведение проверены `promtool`: `promtool check rules monitoring/alert_rules.yml` и шесть модульных тестов в `monitoring/alert_rules_test.yml` (сервис упал, модель не загрузилась на одном из двух экземпляров, рабочий режим отправил обращение сам, ошибки 5xx, всплеск P1, спокойный поток без алертов).

Кроме того, Prometheus 3.5 запускался против двух экземпляров сервиса в той же связке пакетов, что и образ Docker: первый с моделью и потоком демонстрационных запросов, второй без модели. Через пять минут сработали ровно два алерта: RouterModelNotLoaded на экземпляре без модели и RouterRiskSpike, потому что в демонстрационном потоке каждое девятое обращение было о взломе аккаунта (11% обращений с P1 при пороге 5%). Остальные девять правил остались неактивными. Эта проверка нашла ошибку в первом варианте правила RouterModelNotLoaded: `max()` по экземплярам прятал упавший экземпляр за здоровым, теперь правило срабатывает по каждому экземпляру отдельно.

## Откат и переобучение

1. Откат: `docker compose up -d` с предыдущим тегом образа. Модель лежит внутри образа, поэтому код и модель откатываются вместе.
2. Переобучение: `python -m support_router.train --out models`, затем `pytest`, затем сборка образа. Скрипт повторяет шаги ноутбука и даёт ту же модель: на 3 442 фразах вероятности совпали с ноутбуком до последнего знака.

## Чего здесь пока нет

- Уведомлений. Правила видны в Prometheus, но никому не пишут. Для работы нужен Alertmanager с маршрутом: `critical` дежурному сразу, `warning` в общий чат.
- Оценки точности на живом потоке. Модель не знает правильных ответов. Нужна выборочная ручная разметка, например 50 обращений в неделю, с подсчётом доли верных тем и ложных P1.


## MiniLM недоступна

Если растёт `router_semantic_decisions_total{status="UNAVAILABLE"}`, проверьте доступность `model.onnx`, `tokenizer.json` и `encoder_manifest.json` в каталоге `encoder/` рядом с рабочей моделью, зависимости ONNX Runtime и tokenizers, а также поддержку x86-64/AVX2. Сверьте SHA-256 с паспортом. Основной классификатор при этом продолжает отвечать. Для незнакомой фразы ответ содержит `semantic_status="UNAVAILABLE"` и решение о ручном разборе. Обычный отказ слабой семантической подсказки обозначается `ABSTAINED`.
